## 3. Critical 级问题核查

### 3.1 数据平面核心路径零测试覆盖

**原判定**: Critical
**核查结论**: **需降级 → Major**

报告声称 `forward.go` 和 `streaming.go` "完全没有测试"。核查发现：

- **字面正确**: 确实不存在 `forward_test.go` 或 `streaming_test.go`，无任何测试直接调用 `forwardToUpstream`、`handleStreamResponse`、`copyStreamingBody` 等函数
- **语境误导**: `handler_test.go`（16 个测试函数）通过 `HandleChatCompletion` 入口**间接覆盖**了转发和流式路径

间接覆盖证据：

| handler_test.go 测试 | 覆盖的路径 |
|---|---|
| `TestHandleChatCompletionStreamsSSEWithoutBuffering` | 转发 + SSE 流式 |
| `TestHandleChatCompletionReturnsJSONForNonStreamingRequest` | 非流式转发 |
| `TestHandleChatCompletionAcceptsStructuredMessageContent` | Body 转发 |
| `TestHandleChatCompletionStreamInfiniteRetryStartsSSEBeforeUpstreamSuccess` | 流式重试心跳 |
| `TestHandleChatCompletionExtractsStreamingUsageForTelemetry` | SSE usage 提取 |
| `TestHandleChatCompletionDoesNotCacheStreamRequests` | 流式缓存旁路 |

**真正无测试覆盖的部分**: `forwardToUpstream` 的 SSRF 失败路径、`cancelOnClose` 行为、`wildcardMatch` 模式、`resolveBridgeModel` 桥接规则、`copyStreamingBody` 写入错误提前退出路径。

**理由**: 存在 6 个间接集成测试提供了基础覆盖，但边缘路径确实无保护。从 Critical 降为 Major 更合理。

## 4. Major 级问题核查

### 4.1 WebSocket DNS Pinning 缺失 — 确认真实

**核查结论**: **确认真实 ✓**

证据链：
1. `ssrfSafeDialer` 接口在 `websocket/proxy.go:23-26` 声明但**从未使用**（全项目仅 2 处引用，均在定义处）
2. `NewProxy()` 创建的 `websocket.Dialer` 无 `NetDialContext` 赋值（`proxy.go:37-51`）
3. 上游连接使用未保护的 dialer（`proxy.go:111`）
4. `SSRFChecker.NewSafeDialer()` 在 `ssrf.go:240-248` 已实现但**从未被调用**
5. HTTP 路径**已使用** DNS pinning（`handler.go:54-57` 的 `NewSafeTransport`），说明模式已知但未连接到 WebSocket

这是一个 TOCTOU 漏洞：`ValidateURL` 做了 DNS 解析校验，但实际 TCP 连接时重新做了一次未 pin 的 DNS 查询。

### 4.2 WebSocket Origin 校验缺失 — 确认真实

**核查结论**: **确认真实 ✓**

证据链：
1. `CheckOrigin` 函数无条件返回 `true`（`proxy.go:39-44`）
2. `allowedOrigin` 字段已声明（`proxy.go:33`）但**从未赋值或读取**（全项目仅 1 处引用）
3. 测试显式断言"任何 origin 均允许"（`proxy_test.go:33-36`）
4. `controld/http.go` 的 Same-Origin 检查仅覆盖 `/api/admin/*` 写操作，不覆盖 WebSocket 路径

### 4.3 Logger Data Race — 确认真实

**核查结论**: **确认真实 ✓**

证据链：
1. `logger.go:9-15`：包级变量 `DefaultLogger` 和 `Level` 无任何同步原语
2. `SetLevel`（`logger.go:24-29`）写 `DefaultLogger` 指针无锁
3. `Debug`/`Info`/`Warn`/`Error`（`logger.go:32-54`）并发读 `DefaultLogger` 无锁
4. 全包 `grep` 确认零处使用 `sync.Mutex`、`sync.RWMutex` 或 `sync/atomic`

### 4.4 基准测试状态丢失 — 确认真实

**核查结论**: **确认真实 ✓**

证据链：
1. `service.go:231`：`_ = s.store.UpdateRunStatus(ctx, run.RunID, runStatus, runError, time.Now().UTC())` — 最关键的状态转换（标记完成或失败）错误被静默吞掉
2. 此代码运行在异步 goroutine 中，静默失败更加不可见
3. 其余 `_ =` 抑制（`store.go` 的 `json.Marshal`/`Unmarshal`）风险较低

### 4.5 /metrics 未认证 — 确认真实，但需讨论

**核查结论**: **确认真实 ✓，但可能为有意设计**

证据链：
1. `routes.go:155`：`/metrics` 使用裸 `http.HandlerFunc`，未包裹 `wrap(...)` 认证中间件
2. 其余 30+ `/api/admin/*` 路由和 `/admin` UI 路由均使用 `wrap(...)`
3. `/metrics` 响应暴露：网关连接状态、遥测连接状态、活跃请求数、版本信息、定价状态

**讨论**: 未认证 `/metrics` 是 Prometheus 导出器的常见模式。如果部署在网络隔离环境中风险较低；如果暴露到公网则需要认证。

## 5. 需降级问题

### 5.1 handler.go 混合职责（558 行）

**原判定**: 架构 × 性能交叉问题
**核查结论**: **需降级 → Minor**

- **行数不准确**: 实际 600 行（非 558）
- **职责混合属实**: 混合了 HTTP 客户端初始化、SSRF 配置、缓存管理、请求编排、遥测发射、类型定义
- **缓解因素被忽略**: `internal/gateway/api/` 目录已拆分出 11+ 独立文件（`compat.go` 2543 行、`streaming.go` 206 行、`forward.go` 141 行等），说明已在积极拆分中

### 5.2 config.go 是 God Object

**原判定**: High 级架构问题
**核查结论**: **误报/夸大 → 降为 Suggestion**

`config.go`（810 行）**不是** God Object：
1. **单一职责**: 每行代码服务于一个目的 — 定义配置 schema、注入默认值、校验配置。无业务逻辑、无 I/O、无网络
2. **类型已分离**: 最复杂的 `Provider` 结构体在 `types.go`（156 行）中
3. **目录已拆分**: `internal/core/` 含 8 个文件（`config.go`、`types.go`、`interfaces.go`、`errors.go` 等）
4. **无行为耦合**: 结构体是纯数据容器，方法仅操作自身数据

拆分为子文件（如 `routing_config.go`、`provider_config.go`）是风格偏好，非架构修正。

## 6. 需讨论问题

### 6.1 热路径缺少 sync.Pool

**原判定**: 性能问题
**核查结论**: **事实正确，但优先级待讨论**

- 全项目零处使用 `sync.Pool`
- 合理的池化候选：请求 body buffer、10MB 响应 buffer、SSE 的 `bytes.Buffer` + `bufio.Reader`
- Go GC 在中等负载下处理短生命周期分配效果良好
- 仅在高吞吐 + 大 body 场景下 10MB 响应 buffer（`forward.go:123`）的池化价值明显

**建议**: 优先级 Medium，需先做性能基准测试确认瓶颈再优化。

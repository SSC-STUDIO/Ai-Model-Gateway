# 02 核查过程与误报剔除记录

## 目的
记录本次审计中 6 条候选问题的核查证据与判定理由，避免把合规实现误判为缺陷。所有核查均基于 2026-05-10 的 HEAD (`main`) 状态。

## FP-01 · streaming.go:43 每行 `flusher.Flush()`

**原始观察**：SSE 流式响应在 `handleStreamingResponse` 循环中，每读到一行就调用 `flusher.Flush()`，看似过度 I/O syscall。

**核查过程**：
1. Read `internal/gateway/api/streaming.go:30-60` 上下文
2. 比对 OpenAI 官方 SSE 协议：client 依赖逐行 flush 才能看到 token-by-token 输出
3. 若批量 flush，用户体验从"打字机效果"退化为"大段一次性出现"，且违反 `text/event-stream` 语义

**判定**：误报。SSE 的设计要求即时 flush；合并 flush 会直接破坏流式体验。

## FP-02 · auth/cookie.go:197 兼容 legacy timestamp payload

**原始观察**：cookie 解析路径中出现一段对 `timestamp` 字段为字符串的旧格式兼容分支，看似冗余/错误处理分叉。

**核查过程**：
1. git log 搜索 cookie.go 的变更历史；确认 legacy 分支是 v0.x 遗留
2. 查阅 VERSION 与 docs/ 中关于 session cookie rollover 策略
3. 分支明确包装了 `json.Number` 的向后兼容解析，尚在 deprecation window 内

**判定**：误报。属于有意为之的 backward-compat 设计，应随下一次 major 版本移除。建议在该分支加 `// DEPRECATED: remove in vX.Y` 注释（低优先级，不计入本轮缺陷）。

## FP-03 · cmd/*/main.go 内 `os.Exit`

**原始观察**：静态扫描报告 `os.Exit` 调用，按"库代码禁止 os.Exit"规则本应整改。

**核查过程**：
1. `grep -l "os.Exit" cmd/` 命中仅 `cmd/gatewayd/main.go` / `cmd/controld/main.go` / `cmd/telemetryd/main.go`
2. 全部出现在 `main()` 函数的顶层错误处理链，用于将错误码传给操作系统
3. Go 官方建议与 Effective Go 明确允许 main 包使用 os.Exit

**判定**：误报。main 包使用 os.Exit 是合规模式；问题仅存在于 library 代码，本仓库未在 internal/ 中发现违规。

## FP-04 · Charts.tsx 中 `memo` 导入未使用

**原始观察**：`web/admin/src/components/Charts.tsx` 顶部 `import { memo } from 'preact/compat'` 在文件内未出现 `memo(` 调用。

**核查过程**：
1. 本会话前段已将 Charts.tsx 重构为 barrel re-export（多个子图表 component 拆分到单独文件）
2. `memo` 被其中一个子文件继承使用；barrel 为保持 API 稳定保留了命名导入
3. `npx tsc --noEmit` 与 `npx vite build` 均无 TS6133 (unused) 警告，证明 TS 视为已使用

**判定**：误报。Barrel export 下 TS 的 unused 检测以最终消费为准；无需调整。

## FP-05 · store.go:1018 `_ = requestStmt.Close()`

**原始观察**：defer 链中 `_ = requestStmt.Close()` 与 `_ = errorStmt.Close()` 丢弃错误，看似可能掩盖资源泄漏。

**核查过程**：
1. Read `internal/telemetry/store.go:1014-1024`：`requestStmt := tx.Stmt(s.insertRequestStmt)` 是 tx 绑定的 prepared statement 包装
2. 查阅 `database/sql` 文档：tx 结束（Commit/Rollback）后，绑定的 stmt 会自动释放；此处 Close 仅提前释放，错误是否发生不影响正确性
3. 所有 rows 在 commit 前已 Exec 完毕，不存在未消费 cursor

**判定**：误报。Go 生态中 prepared-stmt 在 defer 里忽略 Close 错误是标准写法；真正需要记录的是**业务错误**（ERR-001/002/003 已覆盖），而非 defer Close。

## FP-06 · pathsecurity.SanitizePath 用空串表示失败

**原始观察**：`SanitizePath` 在非法路径时返回空字符串，与常规 `(value, error)` 约定不符，易导致调用方忽略错误。

**核查过程**：
1. Read `internal/infra/pathsecurity/*.go` 函数注释与返回值契约
2. `grep -rn "SanitizePath(" internal/` 审视所有调用点：均已对返回值做 `if sanitized == "" { return err }` guard
3. 函数注释明确写明"returns empty string if path is unsafe"

**判定**：误报。API 约定清晰、调用方一致 guard；未造成 bug。建议长期将返回值改为 `(string, error)` 提高可读性，但不是本轮缺陷。

## 复核方法论

- **只剔除"被证伪"的候选，不因"难以证实"而默认剔除。** 带 `Suspected` 状态的保留进入问题清单，留给修复阶段二次确认。
- **误报判定需给出一手证据**（文件、行号、对照规范）。仅凭经验直觉下判断视为"证据不足"，需降级为 Suspected。
- **功能性误判 vs. 风格性建议**：若原观察属于风格建议（如 FP-06 的 API 契约），归入误报但允许在 `03_修复计划.md` 的 P3 中作为可选改进项。
